Reconstruct a result and explain exactly what did and did not match

Capability. Reproduce a specified computation and write a discrepancy report whose claims match the evidence. The prerequisite is literature mapping and critical reading: identify the precise work, version, result and assumptions before running code. This chapter executes a small original synthetic reconstruction. It does not reproduce either of the real papers discussed there, and it does not supply new empirical evidence about banking.

We use computational reproduction for rerunning a specified analysis with its inputs and computational conditions; independent reconstruction for implementing its stated calculation again; and replication with new data for a new study addressing the same scientific question. Terminology varies. The National Academies' 2019 report distinguishes reproduction using the original computational ingredients from replication across studies with their own data. State your operational task rather than relying on the label alone.

Matching a number is not the same as establishing that it measures the intended quantity, that the data describe the world accurately or that the research design identifies a causal effect. Conversely, a different number is not evidence of misconduct. A changed data vintage, an undocumented sample rule, a software difference or a mistake in your own implementation can each produce a discrepancy. The task is to locate and document the difference before interpreting it.

1. Freeze the target and trace the inputs

Write a reproduction contract before changing anything: exhibit and exact version, target quantity, data snapshot, code entry point, output fields, computational environment and comparison criterion. “Reproduce Table 3” is insufficient if the table contains several samples and specifications. Specify the cell, its units and denominator, and whether the target is an estimate, standard error, sample count or figure. Preserve the original inputs and code separately from your modifications.

Provenance is the trace from an observation's origin through transformations to the reported result. Record the producing organization or original generator, retrieval or creation date, release/version, units, identifiers, coverage and permitted access. A file hash helps identify exact bytes; it does not certify that those bytes are accurate or lawfully redistributable. Record the hash algorithm and what was hashed. A hash of a compressed archive is not a description of the variable definitions inside it.

Keep raw inputs, analysis inputs and outputs conceptually separate even when a tiny example embeds them in one script. For a large project, document which operation creates each intermediate file. Common transformations—deflation, currency conversion, deduplication, winsorization and linking entities—can change the estimand. Record what was done and why, not only the name of the function that did it. Do not let a missing value become zero just because zero makes a program run.

As a professional benchmark, the AEA's data and code policy, inspected on 16 October 2026 and labeled February 2026, calls for documented provenance, transformation and analysis code, and instructions linking code to research outputs. It also addresses restricted data. This chapter illustrates a transparent workflow; it does not claim compliance with every journal requirement or authorize release of restricted records.

2. Reconstruct the computation before adding improvements

First run the supplied procedure as documented, preserving logs and failures. Then identify the smallest calculation behind the target and implement an independent check. Compare row counts, keys, units and intermediate totals before comparing the final coefficient. If the analysis fails at data access, record that boundary: you have tested availability, not numerical reproducibility. If only analysis data are available, you can inspect the remaining calculation but cannot verify the unobserved raw-data construction.

A numerical comparison needs an explicit tolerance. Exact integer and rational arithmetic permits exact equality in this chapter. Floating-point solvers may require absolute and relative tolerances tied to numerical error and the scientific question. Do not choose a wide tolerance after seeing a mismatch. Randomized computation requires the generator, seed, draw order and relevant environment; repeated runs of one deterministic seed are not independent scientific replications. Separate numerical approximation, sampling uncertainty and uncertainty about the model or measurement.

Worked case 1. An executed reconstruction from mixed units

Target contract. A fictional note reports that total loan stock for banks observed at both dates, with positive initial stock, grows by 1/50, or 2%, in data vintage toy-v1. The unit of observation is a bank, the dates are simply 0 and 1, and all amounts refer to the same fictional currency. The target is growth of the matched total, not the equally weighted mean of bank growth rates. Missing observations remain missing. No sampling model or causal assignment is supplied.

Provenance and data dictionary. These four records were created for this chapter; no external dataset was downloaded to construct them. Bank identifiers are unique within a vintage. Amount fields accept nonnegative integers or None; the reported unit applies to both dates in a row. Normalize thousands to millions by multiplying by 1/1000. A positive initial amount is required for a bank's proportional change. A zero final amount is an observed zero and remains eligible. The row order is not substantive.

Independent hand reconstruction. B becomes (60,66) million. The matched set is A and B: initial total 100, final total 102, so growth is (100,102,1/50). Individual growth is −1/10 for A and 1/10 for B, giving an equal-bank mean of 0. Growth of a sum instead weights those individual growth rates by initial loan shares 2/5 and 3/5. C and D are excluded from the matched target for missing end and missing start, respectively. The observed-file totals, using whatever is observed at each date, are (120,152,4/15). That last ratio compares changing observed coverage and is not the matched target.

Runnable artifact. Copy the entire program below into reconstruct.py and run python3 -I -B reconstruct.py. It uses only the Python standard library, reads no files, makes no network requests and prints the two version reports. The code is embedded here so it remains available offline. Fraction keeps the supplied calculations exact. Validation uses explicit exceptions, which also operate under Python's optimization flag. The report uses rational strings; 1/50 is a fraction, not a percentage number.

from fractions import Fraction as F
import json

# Original fictional records: (bank, unit, date_0, date_1).
V1 = (
    ("A", "million", 40, 36),
    ("B", "thousand", 60000, 66000),
    ("C", "million", 20, None),
    ("D", "million", None, 50),
)
# A documented correction to one cell, not a replacement of V1.
V2 = tuple((b, u, s, 64000 if b == "B" else e) for b, u, s, e in V1)

def analyze(rows):
    factors = {"million": F(1), "thousand": F(1, 1000)}
    seen, normalized = set(), []
    for row in rows:
        if not isinstance(row, (tuple, list)) or len(row) != 4:
            raise ValueError("each row needs bank, unit, start, end")
        bank, unit, start, end = row
        if type(bank) is not str or not bank or bank in seen:
            raise ValueError("bank IDs must be nonempty and unique")
        if type(unit) is not str or unit not in factors:
            raise ValueError("unit must be million or thousand")
        for amount in (start, end):
            if amount is not None and (type(amount) is not int or amount < 0):
                raise ValueError("amounts must be nonnegative integers or None")
        seen.add(bank)
        normalized.append((bank, None if start is None else start * factors[unit],
                           None if end is None else end * factors[unit]))
    normalized.sort()
    matched, excluded = [], []
    for bank, start, end in normalized:
        if start is None:
            excluded.append(bank + ": missing start")
        elif end is None:
            excluded.append(bank + ": missing end")
        elif start == 0:
            excluded.append(bank + ": zero start")
        else:
            matched.append((bank, start, end))
    if not matched:
        raise ValueError("no matched bank with positive start")
    start = sum(row[1] for row in matched)
    end = sum(row[2] for row in matched)
    observed_start = sum(s for _, s, _ in normalized if s is not None)
    observed_end = sum(e for _, _, e in normalized if e is not None)
    mean_growth = sum((e - s) / s for _, s, e in matched) / len(matched)
    return {
        "excluded": excluded,
        "matched": [b for b, _, _ in matched],
        "matched_end_million": str(end),
        "matched_growth": str((end - start) / start),
        "matched_start_million": str(start),
        "mean_bank_growth": str(mean_growth),
        "observed_file_growth": str((observed_end - observed_start) / observed_start),
    }

if __name__ == "__main__":
    print(json.dumps({"toy-v1": analyze(V1), "toy-v2": analyze(V2)},
                     indent=2, sort_keys=True))

Reconstruction verdict. The toy-v1 matched total reproduces the stated 2% target exactly. The equally weighted mean answers a different question despite using the same matched banks. In toy-v2, the matched totals are both 100 and growth is zero. These are reproducible consequences of the declared inputs and definitions, not empirical validation of a financial mechanism.

3. Change one ingredient and keep a discrepancy ledger

When a result differs, classify the first known divergence. Is the code unable to run, the input unavailable, an intermediate table different, or only the final rounding different? State what you observed and what is still a hypothesis. If possible, hold the original data fixed while changing code, then hold code fixed while changing data. This does not turn debugging into causal inference; it makes the computational source of a difference inspectable.

A correction differs from an extension. Repairing a documented unit conversion can restore the original target. Replacing a loan-weighted aggregate with an equal-bank mean changes the estimand even if you prefer it. Adding new years changes the population and window. Useful extensions belong in separately labeled outputs, not in a silently overwritten benchmark. Preserve the original mismatch, the change, the reason and the resulting comparison.

A neutral clarification request can be drafted with that evidence; a researcher should not publicly infer intent from an unexplained numerical gap.

4. Interpret success and failure at the right level

Use a result-specific status: reproduced within the stated criterion; reproduced after a documented correction; discrepant with a located cause; discrepant with cause unresolved; or not tested because a required input or environment is unavailable. An entire paper may contain several statuses. Report the number and identity of outputs attempted, rather than calling a package “reproducible” after checking its simplest table.

Independent code can detect a programming mistake but can also repeat the same conceptual error. Check the formula against the question, not just against another implementation. In the worked case, two scripts could agree on mixed-unit totals. The independent unit ledger is what exposes the error. Likewise, reproducing an observational regression does not validate its counterfactual assumptions. New-data replication introduces sampling, measurement and context differences; agreement or disagreement requires interpretation relative to those differences.

Restricted data require a different feasible task, not fabricated success. Document the access route and limits, inspect permitted code and metadata, and separate any synthetic test from the unavailable empirical run. Do not redistribute files merely because another researcher sent them. When suitable, a test with artificial records can verify program behavior while revealing nothing about whether the actual estimates reproduce. Say both things.

Complete solutions and evaluation criteria

1. Name the task before claiming success

The rerun is computational reproduction of this program's output; it tests execution agreement, not real-world measurement or causation. Implementing the stated formula independently is reconstruction; agreement helps check the implementation, but shared conceptual mistakes remain possible. A new sample addressing the same scientific question is a replication study under this vocabulary; comparison must consider its uncertainty and context. README inspection is a transparency or availability assessment, not a successful numerical reproduction. Full credit distinguishes all four and their evidence limits. Using another discipline's labels is acceptable if the actual tasks are made explicit.

2. Recompute both estimands

B's normalized final amount becomes 63 million. The matched initial/final totals and aggregate growth are (100,99,-1/100). Individual growth rates are −1/10 and 1/20, so their equal mean is -1/40. Aggregate growth is −1%, whereas the equal-bank mean is −2.5%; the aggregate gives B greater baseline weight. This is a separate hypothetical vintage and must not overwrite V1 or V2.

3. A valid type is not a valid observation

The matched set becomes A,B,C. D has zero initial stock and is excluded by the positive-baseline rule. Matched initial/final totals and growth are (120,102,-3/20); the mean of −1/10,1/10 and −1 is -1/3. The program correctly computes the supplied altered inputs. The newly false statement is that C's final loan stock was observed to be zero; V1 only says it was unobserved. D's missing start has also been falsely converted to an observed zero. A successful run validates neither substitution.

4. Separate a correction from new evidence

The changes (aggregate,mean) are (-1/50,-1/60), or (-2,-5/3) percentage points. The old mean is zero; the new mean is (−1/10+1/15)/2=−1/60. The versions share almost all the same invented records and differ by a stipulated correction, so this is a controlled data-version comparison. It does not provide a new independently collected sample or test a scientific banking claim.

5. Cross data and definition explicitly

Ordered (K1,V1;K1,V2;K2,V1;K2,V2), the table is (1/50,0,0,-1/60). Within either vintage, comparing K1 with K2 isolates the definition/weighting change. Within either definition, comparing V1 with V2 isolates the one-cell vintage change. A diagonal comparison changes both ingredients and cannot attribute the discrepancy to only one. K2 answers an equal-bank question and K1 a loan-weighted aggregate question; each can be valid under its own contract. Prefer the one relevant to the stated question, and label the other as an additional statistic.

6. Report the access boundary

“The code and dictionary were inspected, but the empirical output was not tested because the necessary restricted records were unavailable. I have recorded the access route, requirements and unresolved permission status. Next I will seek an authorized access arrangement or identify an approved independent verifier. Meanwhile, synthetic records can test unit conversions, missing-value handling and program interfaces; those tests do not show that the paper's estimates reproduce.” Full credit names what was done, what was not, why, and a feasible action without promising access or redistributing restricted information.

7. Agreement can preserve a shared error

Both implementations can repeat the same invalid unit addition. Independently inspect each amount's unit and convert B's values to millions before summing; the corrected matched total then yields 1/50. A separate design check asks what counterfactual variation could justify an economic or causal interpretation and whether selection or borrower demand confounds it. The toy records supply no such assignment, so the supported statement remains an accounting description. Repetition with identical bytes adds execution evidence, not independent observations or a causal design.

6. Teach-back and delayed retention

Teach-back. Explain to a colleague why the V1 result can be reproducible while V2 gives a different answer, and why two matching programs can still be wrong. Use the units, sample and target rather than saying only “versions matter.”

Answer guide

The V1 contract fixes its data and matched-total formula. A correction to a recorded value creates a distinct V2 input and hence a different target result. Separately, matching programs can add incompatible units or implement the wrong estimand. Agreement must be supplemented by a measurement and question check. Neither the version difference nor the common programming error establishes intentional deception.

Delayed retention. After a week, a collaborator sends only a new spreadsheet with a familiar filename and a screenshot of a result. Draft a response plan containing the minimum information needed before declaring reproduction successful.

Criteria and illustrative plan

Preserve the received bytes and record the source/date; identify the intended exhibit, data version, units, population and formula; request or locate the transformation and analysis steps and required environment; compare against the specified target using a declared criterion; retain logs and unexplained discrepancies. A screenshot alone is insufficient to establish the computation. If provenance or access remains unresolved, state “not yet tested” with the missing item, rather than guessing which vintage the filename represents.
